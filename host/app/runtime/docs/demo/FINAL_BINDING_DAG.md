# 双应用最终绑定的无环构建关系

2026-10-20；范围为离线候选，尚未生成最终发布、镜像或板端准入。

## 已核查事实

- 实际 RV32 attempt6 的 `.tbss` 模板地址与 `.got` 起始地址重合。这是冻结 CRT 链接布局；每 hart 的实际 TLS 分配从 `_end` 开始，不能把整个 `.tbss` ELF 模板范围当作全局可变区豁免校验。
- 程序12真实链接的只读表为6307840字节，地址0x80110000；代码与64 hart TLS的实际运行范围为123840字节。它使用原 CODE 角色中的单独只读区，公开请求仍为176字节，绑定仍为512字节。
- HUNet 程序9装载器会对当前 `/proc/self/exe` 求哈希，并与绑定中的 CPU 摘要和 `cpu/gelu.elf` 比较。最终双应用 ELF 不能沿用旧命令行 ELF 的摘要。
- 现有 HUNet measured 准入包含归一化后的512字节绑定摘要。CPU 摘要变化会改变准入身份，不能把旧 flags=7 记录改写成新候选通过。

## 构建顺序与裁定

1. 冻结生产源码的精确路径、字节和 SHA 清单；明确排除最终生成绑定头、外部载荷、日志及收据，以免形成自哈希。
2. 从实际 RV32 ELF、原生资产清单、graph/layout 和已冻结内核配置产生受信任元数据；运行程序的自身摘要位置留空，不把空位称为完成的绑定。
3. 交叉编译真实双应用 ELF。运行时 provider 根据已编入的元数据和自身 ELF 摘要验证外部绑定，再安装真实适配器。
4. 用实际 ELF SHA 补齐 Mosaic runner 和 HUNet CPU 字段，生成最终外部绑定与内核受信任头。不能修改旧程序、权重、尺度、CPU 算法合同、作业表或历史失败记录。
5. 交叉编译匹配内核/驱动，再构建并审计 rootfs、DT、启动文件和实际内建绑定。源码、交叉编译、镜像和板端分别验收。

HUNet `profile_sha256` 继续标识其冻结的 profile4 软件合同；实际所用 S8 bit/XSA 另由本次硬件交付清单和 Mosaic 绑定的 bit/XSA 字段追溯。不能把 profile4 历史 JSON 中的旧 bit 字段解释为本次物理镜像身份。双应用请求的 hardware identity 应使用本次实际硬件清单摘要，独立于继承的 profile 合同摘要。

Ruling: 新 CPU ELF 对应的 HUNet measured gate 只生成明确 pending 的 flags0占位，绑定摘要指向新候选，历史审计摘要与 runId 留空。该占位应在 GPU START 前拒绝推理。代价是离线镜像完成后仍需要独立、获授权的新绑定数值准入，不能把离线镜像构建称为可直接接受的 HUNet 性能测试。

Ruling: 可变区由实际 ELF 的非 TLS、非执行 SHF_WRITE 段与 `_end` 后的64 hart TLS分配区计算、排序和合并；不豁免只读表、参数区、代码或 `.tbss` 模板的额外范围。范围和只读表 SHA 纳入私有 runtime 摘要。代价是生成器与驱动必须逐字节使用同一规范，另用 C 实现交叉复核。

## 学习反问

为什么不把最终 ELF 哈希直接写入该 ELF，再编译一次？

作答：写入哈希会改变 ELF 字节，从而改变自身哈希，不能通过“再编译一次”得到稳定身份。应在编译时冻结不依赖自身摘要的元数据，编译后生成外部绑定，并让内核的受信任绑定和运行时自校验共同检查实际文件。
